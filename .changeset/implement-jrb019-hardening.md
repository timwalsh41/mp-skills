Both implementation orchestrators are hardened against the failure modes observed in the JRB-019 `/implement` run. Each host check command is now preflighted before any child launches: the orchestrator runs every configured lifecycle, PR, and merge check once under `/bin/sh` (the shell host gates actually use, not the lead's bash) and rejects the launch when a command cannot execute (shell syntax error, missing binary), instead of letting it abort a gate mid-run after work has started, as a bash-only `$((10#...))` arithmetic check did. Exit 0 and 1 remain valid state verdicts and pass. The transition children in both scripts now carry an explicit phase-boundary rule baked into their task text: if the issue is already in the requested phase's target status, report `TRANSITION_ALREADY_SET` and post nothing; never advance past the requested phase, and never let a lead-supplied tracker hint justify a transition to a different status (a hint that said "In Progress is already applied" previously caused a premature Ready for Review write with no PR in existence). A review fix that legitimately changes nothing (every finding adjudicated out of scope) is now a verified fix-loop outcome instead of a dead end: a host gate proves the captured patch is empty, the fixer's worktree is clean and uncommitted, and the integration branch is green, and the fix loop proceeds to fresh reviews without spawning a merger that would refuse an empty patch and escalate forever. Finally, the shared-helper copies the two scripts carry (the workflow sandbox has no imports) are widened and pinned: helpers that had drifted between `implement` and `implement-spec` (gate and control construction, failure classification, argument validation) are unified, and the parity tests now assert byte-identical copies for all nineteen shared helpers, the transition phase-boundary text, the worker lifecycle schemas, and the merger gate body.
